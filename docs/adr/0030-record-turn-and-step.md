# ADR-0030：记录带上请求发出的轮次与步数

- 状态：Accepted（2026-11-02）
- 相关：`src/steps.ts`、`src/index.ts`、`src/engine.ts`、`src/records.ts`、`src/client/view.ts`、`src/client/StatsParts.ts`、ADR-0020、ADR-0024、ADR-0028

## Context

ADR-0028 让每个值带上它在 body 里的位置，界面标出 `messages.556` 这样的消息序号。它答的是「值在那次请求的哪条消息里」，而用户真正要办的事是「回到会话里找到这一次请求」。两件事靠不上：

- `messages.N` 是**那次请求**数组里的下标，从 0 起算。历史被压缩或截断后，同一条消息在后续请求里的下标会变，它不是一个稳定的坐标。
- 记录行只有时间和「工作区 · 会话标题」。同一个会话一轮里往往发好几个请求（每个 step 一次，工具调用后又一次），光看时间分不清是哪一步。

会话里本来就有稳定的坐标：轮（turn）和步（step），「轨迹」标签页显示的就是这两个数。插件只是看不到它——网关看到的是一个 HTTP 请求，不知道它是哪一步发的。

## Decision

- 订阅宿主的 `session/event`，只读 `step/start`：它的 payload 就是 `{turn, step}`，且由 agent loop 在**发起模型调用之前**追加，所以请求到达网关时，这个会话最近的 `step/start` 就是它所在的这一步。
- `StepBook`（`src/steps.ts`）按 session id 记住每个会话最近一次 `step/start` 的 `{turn, step}`。一个会话一条记录，最多 `MAX_BOOK_SESSIONS = 500` 条，超出按「最久没开口」的顺序淘汰；被忘掉的会话，其请求照旧记录，只是没有轮次步数。
- 记录新增 `turn`、`step` 两个字段（ADR-0008 的「不含真值」不变，它们是数字），在 `base()` 里与 `title`、`workspace` 一起写入，来源是 `EngineOptions.steps`。老记录没有这两个字段，界面不显示。
- 一个 step 一直有效到下一条 `step/start`：agent 在步与步之间发出的调用（压缩、生成标题）记为最近的那一步，这是能给出的最接近的答案，胜过没有。
- 界面：记录行在「时间」后加一列「轮·步」，显示 `42·3`，悬停与无障碍名读「第 42 轮 · 第 3 步」；展开后明细顶部再用整句写一遍。窄屏（≤640px）与「来源」列一起隐藏，明细里仍有整句。
- 两字段成对：读盘（`parseRecord`）与浏览器侧（`stepOf`）都只接受都是 ≥1 的整数的成对值，只有一个的一律丢掉，免得界面把半个坐标当坐标画。

## Consequences

- 一行记录现在能对上「轨迹」里的一步：时间说它是这个会话的第几次请求，轮步说它在会话里的哪一步，`messages.N` 与前后文字说值在请求的哪条消息、什么上下文。三者互补。
- host 侧多一个 `session/event` 监听：每个会话事件过一次 `event.type` 比较，其余什么也不做。`step/start` 一轮只有几次，开销在噪声里。
- 不落盘、不进统计：`StepBook` 是内存里的一个 Map，重启后从下一条 `step/start` 重新开始。重启后、反向代理重放的历史请求本来就没有轮次可言，留空是对的。
- 未加 `{global: true}` 是故意的：插件在根上下文，未打作用域的监听者按 `dsh-scope` 的规则本来就能收到每个作用域的事件，子会话也在内。只有监听者自己被打上作用域时才需要它。
- 局限：`turn`/`step` 是 host 给的当前值，不是请求里带的；若一个会话在同一进程里有两条并行的调用链（同一 session 并发发两个请求），两者都会记成最近的那一步。会话内的调用是顺序的，所以只在异常用法下才会碰到。
